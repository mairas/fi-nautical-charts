# Working on this repository

Tooling that turns Finnish open nautical charts into MBTiles chart sets for
Signal K and Freeboard-SK. `README.md` documents what each tool does and why the
processing is the way it is; read it before changing any of them. This file is
the shorter thing: the rules that are not obvious from the code, and the ones
that are easy to get wrong.

Host names, paths and deployment specifics are deliberately absent. **This
repository is public.** They live in `CLAUDE.local.md`, which is gitignored.

## Rules that are not negotiable

These came from the chart user, not from a style preference. Breaking one
produces charts that are worse in a way that is hard to see and hard to undo.

- **Never merge or flatten chart data.** Each product is a separate MBTiles
  layer, individually switchable in the chart software. Do not combine sources
  into one file, ever, however much duplication there appears to be.
- **Never retire Satamakartat.** The harbour charts carry genuinely more detail
  than the coastal series at the deepest levels — real multiscale generalisation,
  not an upscale.
- **Never recover completeness with a full-grid sweep.** Any fix for missing
  tiles must be a pruned method that is provably gap-free. `fill` mode exists
  because of this rule; a `TileMatrixSetLimits` sweep is not an acceptable
  fallback even once.
- **Publish by rename, never by transfer.** Build beside the target on the same
  filesystem and `rename()` into place. An upload once truncated three of five
  files and nobody noticed for six days.

## Chart-domain decisions the code depends on

**Downscale only the layers that need it.** A layer whose lower zooms are
degraded rescales of a genuine deepest level is rebuilt from that level. A layer
that Traficom renders *per zoom* — small-scale overviews, and vector-derived
sources — must not be: downscaling crams large-scale detail into a small-scale
sheet and destroys the generalisation the cartographer did.

**The downscale source zoom is per layer and explicit, never inferred.** Taking
"the deepest level present" is wrong for a layer whose deepest level is itself an
upscale, and it silently destroys place names a few levels down. The layer table
carries the number.

**Edition dates are recorded at fetch and never re-derived.** The tile server
renders on demand and stamps what it just made, so a `Last-Modified` sampled
later reports the day *we* downloaded, indistinguishable from a real new edition.
Nothing in the data separates them; only the response's own `Date` header,
during the request that caused the tile, does. That is why the recording lives at
the single HTTP call site and why `currency.py` has no network code at all.

**The download baseline advances only after every zoom completes.** It is the
`If-Modified-Since` value for the next refresh. Advancing it per zoom means an
interrupted run sends a future baseline next time, and the server answers a
future `If-Modified-Since` with `304` for everything — unchecked tiles are then
skipped forever while the run exits 0.

**Metadata describes what an archive holds, not what was requested.** A run that
stopped early must not stamp the zoom range it was asked for. The console warning
scrolls away; the metadata is what clients read.

**Names are stamped once and rebuilds carry them forward.** `strip-nodata` and
`downscale` copy the metadata table verbatim, so rebuilding from an older
download re-imports its older name. Relabelling reads only stored metadata, so
it is cheap and safe to redo.

## Conventions

**`./run` is the entry point for everything.** A bash dispatcher: each target is
`function name {`, then a `#@ Description` line, then a `#@ Category: X` line, in
exactly that order. The help text is generated by walking the file with awk, so a
line out of order drops the target from `./run help` silently while leaving it
runnable. There is no Makefile and there should not be one.

**Python runs through `uv`, never pip.** Every tool is a single file with PEP 723
inline metadata. The ones the monthly pipeline invokes as subprocesses also carry
a committed `<script>.py.lock`, and run under `--locked` so an unattended run
resolves nothing. `./run relock` is how a dependency moves — as a commit someone
read, not at 01:00 on the first of the month.

**Layout is flat and scripts are co-located on purpose.** Tools derive sibling
paths from their own location, and several import each other. Keep them in one
directory.

**`./run test` names its test files explicitly.** A bare `pytest` collects the
whole tree including scratch files. Add a new test file to that list or it will
not run.

## Testing

Test behaviour, not implementation. Write the failing test first for anything
that changes behaviour.

The pipeline's orchestration is tested through a stubbed step runner, because
what makes it safe to run unattended — a failing layer does not stop the rest,
`--dry-run` contacts nobody, scratch does not survive a failure — lives in the
sequencing rather than in any one step. The steps have their own tests.

**Before trusting a pass, name the input that would make it fail.** Three
verification anti-patterns have each produced a confident green result here:

- *Fixtures wholly inside the thing under test.* Boxes chosen inside a coverage
  mask made the pruned run and the exhaustive run enumerate the same tiles, so
  the comparison proved nothing at "0% fewer requests". Fixtures must straddle
  the boundary they are testing, and must carry the relation they are meant to
  have so the run fails when it does not hold.
- *Testing a copy of the code.* A chunking check compared a local
  reimplementation against itself and would have survived the transposed index it
  named in its own docstring.
- *Agreeing on nothing.* A comparison passed when both sides found zero content.
  Zero has to be a failure, not agreement.

**Test at a parameter's default value.** A guard verified only at a non-default
setting shipped broken: at the default, the whole world is one tile and every
input landed inside it.

**Resume markers must version the algorithm, not just the inputs.** Changing
which tiles are eligible without changing any argument let a re-run report
"already complete" having fetched none of the tiles the fix existed to recover.

## Code style

YAGNI, KISS, DRY. Only what was asked for. No error handling for impossible
states, no abstraction for a single caller, no design for hypothetical futures.

Comments are dense here by deliberate choice, and every one of them explains
**why the code is the way it is** — usually which alternative was tried and what
it cost. Never write what changed or why it changed: write for a reader who never
saw the diff. A comment that only restates the code should not exist.

Documentation describes current state. No development history, no
implementation-status language, no "we used to".

## Working in the open

This repository is public.

Infrastructure detail leaks through *reasoning*, not through carelessness with
secrets — host names and service inventories get written down because they are
the honest justification for a design decision. Express the constraint as a
property of the work instead: "the build host is modest and shared with unrelated
services" carries the whole consequence without naming anything.

**Editing does not remove it.** GitHub keeps every revision of an issue, PR or
comment body and serves the diff. A comment can be deleted and reposted, which
purges its history; an issue body can only be purged by deleting the issue; a PR
body has no API at all and needs a per-revision delete in the web UI. So the
check belongs *before* writing, not after.
